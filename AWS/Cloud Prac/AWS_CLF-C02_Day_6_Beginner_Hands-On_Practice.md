## Day 6: Beginner Hands-on AWS Practice

This lesson turns the theory from Days 1–5 into practical experience.

Approximately **45–60 minutes**.

## Safety and cost rules

Before creating resources, remember:

- AWS pricing and account offers can change.
- Do not assume that every resource is free.
- Use small test data only.
- Keep the S3 bucket private.
- Do not create access keys for the root user.
- Do not place passwords or access keys in code.
- Complete the cleanup section after the exercises.
- A budget alerts you about cost; it is not automatically a hard spending limit.

> These exercises intentionally avoid EC2 and RDS because a beginner can accidentally leave those resources running.

# Lab 1: Create a cost budget

## Why do this first?

Before experimenting with cloud resources, you should have visibility into spending. This lab connects to the Day 4 concepts:

- AWS Budgets
- Actual cost
- Forecast cost
- Threshold notifications

## Steps

1. Sign in to the AWS Management Console using an administrative identity. Avoid everyday use of the root user.
2. Search for **Billing and Cost Management**.
3. In the navigation menu, choose **Budgets**.
4. Choose **Create budget**.
5. Select a simplified template if available, or create a customized **Cost budget**.
6. Give it a clear name, such as:

   ```text
   beginner-aws-monthly-budget
   ```

7. Enter a small monthly amount appropriate for your own account and learning plan.
8. Add your email address as a notification recipient.
9. Configure an alert for actual or forecast cost approaching the budget.
10. Review the settings and create the budget.
11. If AWS sends a confirmation message, follow the instructions in that message.

Console wording can vary by account experience. The current official process is documented in [Creating a budget – AWS Documentation](https://docs.aws.amazon.com/cost-management/latest/userguide/budgets-create.html).

## What you learned

- **AWS Pricing Calculator:** Estimates a planned architecture
- **AWS Cost Explorer:** Analyzes existing costs and trends
- **AWS Budgets:** Tracks thresholds and sends alerts

## Check your understanding

**Question:** Will the budget automatically delete your resources when the amount is reached?

**Answer:** Not simply by creating an alert. AWS Budgets monitors actual or forecast values and sends notifications. Selected budget actions require separate configuration.

# Lab 2: Store an object in Amazon S3

## Scenario

Your application produces a daily payment report. You want to store the report securely as an object in AWS.

This lab teaches:

- S3 buckets
- Objects and keys
- Regions
- Private access
- Object storage

## Step 1: Prepare a local file

On your Mac, open TextEdit or VS Code and create a file named:

```text
payment-report.txt
```

Add this sample content:

```text
Payment report
Date: Training Day
Transactions: 3
Successful: 2
Failed: 1
```

Save the file somewhere easy to find, such as your Desktop.

## Step 2: Create an S3 bucket

1. In the AWS Console, search for **S3**.
2. Open the Amazon S3 service.
3. Choose **Create bucket**.
4. Select a general-purpose bucket when asked for the bucket type.
5. Enter a globally unique bucket name, for example:

   ```text
   venkatesh-clf-practice-unique-number
   ```

   Replace `unique-number` with a value that makes the complete name unique.

6. Select an AWS Region close to you or the Region you use for training.
7. Leave **Block Public Access** enabled.
8. Leave the remaining options at their safe defaults for this exercise.
9. Choose **Create bucket**.

AWS explains the current console workflow in [Getting started with Amazon S3](https://docs.aws.amazon.com/AmazonS3/latest/userguide/GetStartedWithS3.html).

## Why must the bucket name be unique?

General-purpose S3 bucket names belong to a shared global namespace. Another AWS account might already own the name you first try.

## Step 3: Upload the object

1. Open the bucket you just created.
2. On the **Objects** tab, choose **Upload**.
3. Choose **Add files**.
4. Select `payment-report.txt`.
5. Keep default permissions and storage settings.
6. Choose **Upload**.
7. Confirm that the upload succeeded.

The current upload procedure is described in [Uploading objects – Amazon S3](https://docs.aws.amazon.com/AmazonS3/latest/userguide/upload-objects.html).

## Step 4: Inspect the object

1. Select the uploaded object's name.
2. Review its properties.
3. Notice the following concepts:

   - **Bucket:** The container
   - **Object:** The stored file plus metadata
   - **Key:** The object's unique name inside the bucket
   - **Region:** Where the bucket is located
   - **Size:** Amount of stored data

4. Download or open the object through your authenticated console session to verify its contents.

## Important security lesson

Do not make the bucket public just to open the object through a public URL. The correct access method depends on the application. Public access should be enabled only when there is a clear requirement and appropriate security design.

## S3 vs EBS vs EFS

| Requirement | Correct service |
|---|---|
| Store reports, images, logs, or backups as objects | Amazon S3 |
| Attach a persistent virtual disk to EC2 | Amazon EBS |
| Share a Linux file system between compute resources | Amazon EFS |

## Check your understanding

1. Is `payment-report.txt` a bucket or an object?
2. Is S3 object, block, or file storage?
3. Why did we leave Block Public Access enabled?

### Answers

1. An object
2. Object storage
3. Because this training report has no requirement for public internet access

# Lab 3: Create and test an AWS Lambda function

## Scenario

You want a small serverless function that receives payment details and returns a simple status response.

This lab connects these concepts:

- Serverless compute
- Events
- Function execution
- Automatic scaling
- Pay-for-use model
- IAM execution roles

## Step 1: Open Lambda

1. In the AWS Console, search for **Lambda**.
2. Choose **Create function**.
3. Select **Author from scratch**.
4. Enter this function name:

   ```text
   clf-payment-status-practice
   ```

5. Choose a currently supported **Node.js** runtime.
6. Keep the default architecture.
7. In the permissions section, let Lambda create a basic execution role for this exercise.
8. Choose **Create function**.

The current introductory workflow is available in [Create your first Lambda function](https://docs.aws.amazon.com/lambda/latest/dg/getting-started.html).

## What happened behind the scenes?

AWS created:

- A Lambda function
- An IAM execution role
- Basic permission for the function to send logs to CloudWatch Logs

You did not create or patch a server. AWS manages the underlying compute infrastructure.

## Step 2: Add the function code

Replace the example function code with code matching the runtime's module format. For a CommonJS-style Node.js editor, use:

```javascript
exports.handler = async (event) => {
  console.log("Payment event received:", JSON.stringify(event));

  const amount = Number(event.amount ?? 0);
  const currency = event.currency ?? "NZD";

  if (amount <= 0) {
    return {
      statusCode: 400,
      body: JSON.stringify({
        status: "REJECTED",
        reason: "Amount must be greater than zero"
      })
    };
  }

  return {
    statusCode: 200,
    body: JSON.stringify({
      status: "ACCEPTED",
      amount,
      currency
    })
  };
};
```

If the generated file uses ES modules and contains `export const handler`, use this equivalent declaration instead of `exports.handler`:

```javascript
export const handler = async (event) => {
  // Use the same function body shown above.
};
```

1. Paste the code into the Lambda code editor.
2. Choose **Deploy** to save and deploy it.

## Step 3: Create a test event

1. Open the function's **Test** tab or test control.
2. Create a new private test event.
3. Name it:

   ```text
   ValidPayment
   ```

4. Use this JSON:

   ```json
   {
     "paymentId": "PAY-1001",
     "amount": 125.50,
     "currency": "NZD"
   }
   ```

5. Save the event.
6. Choose **Test**.
7. Review the result.

Expected body:

```json
{
  "status": "ACCEPTED",
  "amount": 125.5,
  "currency": "NZD"
}
```

AWS documents the current test-event process in [Testing Lambda functions in the console](https://docs.aws.amazon.com/lambda/latest/dg/testing-functions.html).

## Step 4: Test a failure scenario

Create another test event:

```json
{
  "paymentId": "PAY-1002",
  "amount": 0,
  "currency": "NZD"
}
```

Expected result:

- Status code: `400`
- Status: `REJECTED`
- Reason: Amount must be greater than zero

## What you learned

When you selected **Test**:

1. The JSON became the Lambda event.
2. Lambda invoked the handler.
3. The function processed the amount.
4. It returned a response.
5. The log statement was sent to CloudWatch Logs through the function's execution role.

# Lab 4: View CloudWatch logs and inspect the IAM role

## Part A: View logs

After invoking the function:

1. Open your Lambda function.
2. Use its monitoring or log-viewing link to open CloudWatch Logs. Depending on the current console experience, logs may also be available from the test area.
3. Open the log group associated with the function. Its name commonly follows this pattern:

   ```text
   /aws/lambda/clf-payment-status-practice
   ```

4. Open the latest log stream.
5. Find the message:

   ```text
   Payment event received
   ```

6. Observe the invocation information generated by Lambda.

AWS documents current log-viewing options in [Viewing CloudWatch logs for Lambda functions](https://docs.aws.amazon.com/lambda/latest/dg/monitoring-cloudwatchlogs-view.html).

## CloudWatch vs CloudTrail

| Question | Correct service |
|---|---|
| What did my function log? | CloudWatch Logs |
| How many errors or invocations occurred? | CloudWatch metrics |
| Who changed or deleted the function through an AWS API? | CloudTrail |

## Part B: Inspect the execution role

1. Return to the Lambda function.
2. Choose **Configuration**.
3. Choose **Permissions**.
4. Find the **Execution role** section.
5. Open the role in IAM.
6. Review the permissions attached to it.

AWS documents the current path in [Viewing and updating Lambda execution-role permissions](https://docs.aws.amazon.com/lambda/latest/dg/permissions-executionrole-update.html).

## Why does Lambda need a role?

Your function runs as an AWS identity. Its execution role determines what the function can do.

For this exercise, it needs permission to write logs. If it later needs to read the S3 report, its role would need appropriate `s3:GetObject` permission for that object or bucket.

## Least-privilege example

Bad design:

```text
Give the Lambda function AdministratorAccess.
```

Better design:

```text
Allow only the required log actions and access to the specific S3 bucket or object required by the function.
```

AWS recommends reducing execution-role permissions to those actually required. See [Defining Lambda function permissions with an execution role](https://docs.aws.amazon.com/lambda/latest/dg/lambda-intro-execution-role.html).

# Cleanup checklist

Complete these steps after the labs.

## Delete the Lambda function

1. Open the Lambda console.
2. Select `clf-payment-status-practice`.
3. Choose **Actions** and then **Delete**, or use the current delete control.
4. Confirm the deletion.

## Delete the Lambda log group

Deleting a Lambda function does not necessarily remove its existing CloudWatch log group.

1. Open CloudWatch.
2. Open **Log groups**.
3. Select:

   ```text
   /aws/lambda/clf-payment-status-practice
   ```

4. Delete the log group.

## Delete the S3 object and bucket

An S3 bucket must normally be empty before it can be deleted.

1. Open the S3 bucket.
2. Select `payment-report.txt`.
3. Delete the object and confirm.
4. Return to the bucket list.
5. Select your practice bucket.
6. Choose **Delete** and complete the confirmation.

## Review the IAM execution role

1. Open IAM.
2. Open **Roles**.
3. Find the automatically created role associated with the deleted Lambda function.
4. Confirm that it is used only by this deleted practice function.
5. Delete it if it is no longer required.

Do not delete a shared role or any role you did not create for this exercise.

## Keep or delete the budget?

Keeping the budget is useful because it continues to provide cost visibility. Delete it only if you no longer want the notification.
